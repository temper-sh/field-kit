# Working on local-ai-setup

How the thing is built, and the invariants that make it safe to re-run. Read
[FINDINGS.md](FINDINGS.md) before changing any engine flag — most of them are
load-bearing for a non-obvious reason.

## Shape

`setup.sh` is an orchestrator. It parses arguments, defines every helper, then
**sources** `steps/*.sh` in order. Steps are not executables and have no
shebang — they run inside setup.sh's shell and use its functions and counters.

```
setup.sh
  ├─ reporting helpers  ok / skip / fail / note / manual / do_install / do_patch / do_change
  ├─ manifest access    manifest_ids / mval / defval
  └─ sources steps/10 → 20 → 30 → 40 → 45 → 50
```

### The reporting contract

Every item a step touches must report exactly one outcome. This is what makes a
re-run readable as an audit rather than as noise.

| helper | meaning |
|---|---|
| `ok "x"` | already in the desired state |
| `skip "x"` | deliberately not done (lazy downloads, opt-in work) |
| `fail "x"` | broken; sets a non-zero exit at the end |
| `manual "x" "cmd"` | needs sudo — prints, never runs |
| `do_install "x" cmd...` | was missing, created it |
| `do_patch "x" cmd...` | existed but had wrong contents |
| `do_change "x" cmd...` | replaced a generated file that had drifted |

`do_*` take a command as **argv, not a shell string** — they `exec` it directly.
Anything needing pipes, redirection or conditionals goes in a named function that
you pass by name:

```bash
do_change "launchd plist (reinstall + reload)" install_plist
```

They also honour `--dry-run` for you: in dry-run they print the line and skip the
command. Never mutate outside a `do_*` helper, or `--dry-run` silently lies.

### Invariants

1. **A second run changes nothing.** `./setup.sh && ./setup.sh` — the second must
   be `[ok]`/`[skip]`/`[manual]` only. `[manual]` persists by design until you
   run the sudo commands.
2. **`--dry-run` touches nothing.** It may create `.state/` and temp dirs; it may
   not touch `$HOME` or the HF cache.
3. **`models.yaml` is the only input.** config.yaml carries a
   `# GENERATED by local-ai-setup — edit models.yaml instead` header;
   models.json marks itself with a `_generated_by` key instead (JSON has no
   comments). Never read `models.example.yaml` from code.
4. **Generated files are replaced only on change**, with a timestamped `.bak`.
   The service runs `--watch-config`, so a config change needs no restart; only a
   changed plist does.
5. **Never run sudo.** Detect, print, move on.
6. **Patching is hash-based**, which makes it self-healing: re-downloading a
   model reverts its template, the next run notices, re-applies.

### bash 3.2

macOS ships bash 3.2 and that is what `#!/usr/bin/env bash` resolves to here. No
associative arrays, no `${var,,}`, no `mapfile`. Use `case` for lookup tables.

### yq gotchas

- `select(.enabled != false)`, **not** `.enabled // true`. The alternative
  operator fires on `false`, which is exactly the value being tested.
- `//` is safe for numeric defaults: `0 // 1800` → `0`, so `ttl: 0` survives.
  It is *not* safe for booleans.
- Never `yq -i` the manifest. It reflows comments and strips the quoting around
  the `--speculative-config` JSON. Reading is fine; writing is not.

## Adding a step

1. `steps/NN-name.sh`, starting with a header comment and a standalone
   `# shellcheck shell=bash` line (it must be its own line — appended to a prose
   line it is silently ignored).
2. Add the name to `ALL_STEPS` and to `step_file()` in `setup.sh`.
3. Add it to `--only`'s documented list in `usage()`.
4. Prefix step-local loop variables with `_` — steps share one shell, so an
   unprefixed `id` will collide with another step's.

## Adding a model

Use `prompts/add-model.md` with a frontier model, paste the entry into
`models.yaml`, re-run. Then actually verify it:

- Does it boot? `curl -s localhost:8080/logs/stream/upstream` on failure —
  llama-swap's own log only ever says `upstream command exited prematurely`.
- Do the flags exist? `rapid-mlx serve --help` from the installed binary, not
  the website (finding #4).
- If it is another Qwen3.6 hybrid, it needs `--hybrid-cache-entries` and an MTP
  sidecar (findings #1 and #3).

## Testing

`tests/run-all.sh` — see [tests/README.md](../tests/README.md). Offline tests are
hermetic and fast; runtime tests need the live stack and will pull GGUFs on first
run. The offline run is the per-change gate; the runtime and perf suites are
on-demand — for a bare engine bump the gate is check 12's shape as a single
curl plus a plain completion (docs/PLAN.md §3a has the runbook), and the full
suite is for llama-server/topology changes or misbehaviour.

```bash
tests/run-all.sh --offline    # no service, no network, ~30s
tests/run-all.sh --runtime    # needs llama-swap up
tests/run-all.sh --perf       # slow: restarts the service, loads 15GB
```

## Uninstall

`scripts/uninstall.sh` is the README removal table, executable (`--dry-run`
first). It removes what the stack owns outright and only *prints* commands
for shared things — brew formulas, the two sudo-written `/etc` files. With
`--provenance <file>` (written by the field-kit probe before it installs
anything; format documented in the script header) it also executes the brew
removals for items the file proves were probe-added. Offline check 21 tests
both modes against a fixture HOME and a brew shim; keep the provenance
grammar in sync with the field-kit repo, which produces it.

## Shellcheck

```bash
shellcheck -x -e SC2329 setup.sh steps/*.sh tests/*.sh scripts/*.sh
```

`SC2329` ("function never invoked") is suppressed wholesale: shellcheck cannot
follow the dynamic `. "$ROOT/steps/$(step_file "$s")"`, so every helper looks
dead to it. Nothing else should be suppressed globally — use a targeted
`# shellcheck disable=` with a reason instead. Note directives cannot sit in
front of an individual `case` branch; put them before the whole statement.

## A trap worth knowing

The machine this was built on had `~/.config/llama-swap` symlinked into a
dotfiles repo whose target had been deleted. `mkdir -p` on a dangling symlink
fails with a bare `ENOENT` that reads like a permissions problem.
`steps/40-configs.sh` detects this and explains it rather than dying — but it
deliberately does **not** delete the symlink. Removing someone's symlink is not
an installer's call.
